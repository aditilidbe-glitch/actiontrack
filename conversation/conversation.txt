  # Smart Commit — Atomic Conventional Commits
  
  Split bulk changes into multiple logical commits that simulate incremental development.
  
  > **Convention:** This skill produces [Conventional Commits v1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) messages (`<type>(scope): <summary>`). For the kernel/Git-style short-prefix convention instead (no `feat:`/`fix:` prefixes), use the `commit-message` skill.
  
  ## Hard Rules
  
  1. **NEVER commit without a ticket ID.** If the user hasn't provided one, stop and ask for it.
  2. **NEVER add `Co-Authored-By` trailers.**
  3. **NEVER mention agents, LLMs, models, Claude, Cursor, AI, or any assistant/tool identity** in the title, body, or trailers.
  4. **NEVER make a single bulk commit** when changes span multiple concerns — always split.
  
  ## Workflow
  
  ### 1. Analyze All Changes
  
  ```bash
  git status --short
  git diff --stat
  git diff HEAD
  ```
  
  ### 2. Group Changes into Logical Commits
  
  Categorize every changed file into one of these groups (in commit order):
  
  | Order | Group                  | Example                                |
  |-------|------------------------|----------------------------------------|
  | 1     | Core module / feature  | New service files, new classes          |
  | 2     | Tests                  | Unit tests, integration tests          |
  | 3     | Schema / config        | JSON schemas, config.py, env changes   |
  | 4     | Prompts                | Versioned prompt files, inline prompts |
  | 5     | Integration / wiring   | Importing + using new code in existing |
  | 6     | Cleanup / chore        | Removed imports, formatting, deps      |
  | 7     | Documentation          | Markdown docs, README updates          |
  
  Within "Integration / wiring", further split by area if files span different domains (e.g., preloaders vs. API vs. celery tasks).
  
  ### 3. Present the Plan
  
  Before committing, show the user a table of planned commits with:
  - Commit number
  - Type and scope
  - Summary
  - Files included
  
  Wait for the ticket ID if not provided.
  
  ### 4. Execute Commits Sequentially
  
  For each group:
  
  ```bash
  git add <files-in-group>
  git commit -m "<type>(scope): <summary>" \
    -m "<description>
  
  refs: <TICKET-ID>"
  ```
  
  ## Commit Message Format
  
  ### Structure
  
  ```
  <type>(scope): <short summary>
  
  <detailed description — problem, solution, impact>
  
  refs: TICKET-ID
  ```
  
  When using git CLI:
  
  ```bash
  git commit -m "<type>(scope): <short summary>" \
    -m "<detailed description>
  
  refs: TICKET-ID"
  ```
  
  ### Title Rules
  
  - Max 60 characters (a project style rule; the spec itself sets no limit — note `<type>(scope): ` counts toward it)
  - Lowercase (except acronyms)
  - Imperative mood ("add X" not "added X" or "adds X")
  - No period at the end
  - Include a scope in parentheses when one applies. Scope is OPTIONAL per the spec — omit it for changes with no single natural scope (repo-wide refactors, merges, lockfile bumps): `chore: regenerate lockfile`
  
  ### Body Rules
  
  - Wrap at 72 characters
  - Explain the "why", not just the "what"
  - Always end with `refs: <TICKET-ID>`
  
  ## Types
  
  | Type     | Meaning                                  |
  |----------|------------------------------------------|
  | feat     | New feature                              |
  | fix      | Bug fix                                  |
  | refactor | Internal code cleanup, no behavior change|
  | docs     | Documentation changes                    |
  | test     | Test-related changes                     |
  | chore    | Maintenance, config, dependency work     |
  | perf     | Performance improvement                  |
  | ci       | CI/CD changes                            |
  | build    | Build system changes                     |
  | style    | Formatting, whitespace only              |
  
  ## Scope
  
  Use the primary module or feature area:
  
  ```
  (auth)                  (api)
  (wellness-agent)        (celery)
  (user-preference)       (pledge-engine)
  (prompt-manager)        (audio)
  (context-pipeline)      (workflow)
  (insight-engine)        (config)
  ```
  
  ## Breaking Changes
  
  A commit that introduces a breaking API/behavior change MUST signal it in one of two spec-compliant ways (either or both):
  
  1. **`!` before the colon** in the title — right after the type/scope:
  
     ```
     feat(api)!: drop support for legacy auth header
     ```
  
  2. **A `BREAKING CHANGE:` footer.** The token MUST be uppercase (`BREAKING-CHANGE:` is an accepted synonym); everything after the colon describes the break:
  
     ```bash
     git commit -m "feat(config)!: require AZURE_STORAGE_CONNECTION_STRING" \
       -m "The blob storage client now fails fast when the connection string
     is unset instead of silently degrading.
  
     BREAKING CHANGE: AZURE_STORAGE_CONNECTION_STRING is now mandatory; deploys
     without it will refuse to start.
  
     refs: SC-950"
     ```
  
  Notes:
  - Use `!` for a scannable signal in `git log --oneline`; add the footer when the consequence needs explaining. Using both is fine and recommended for anything non-obvious.
  - The `!` may combine with a scope (`feat(api)!:`) or without (`feat!:`).
  - Order footers as `BREAKING CHANGE:` first, then `refs:`.
